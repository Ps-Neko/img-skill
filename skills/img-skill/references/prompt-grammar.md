# Prompt Grammar

## Evidence Boundary

- **Account-observed pattern / 계정 관찰 패턴:** 승인된 `@xiaoxiaodong01` 공개 게시물 연구에서 출력 조건, 스타일보다 보존 조건을 먼저 두는 방식, 요소 사이의 관계로 구성하는 방식, 재료와 제작 동작, 역할·면적 기반 색 체계, 구성 요소로 쓰는 타이포그래피, 예상 실패에 한정한 제한, 반복 문법과 가변 항목의 분리가 관찰되었다. 이는 관찰 요약이며 계정 소유자의 의도나 공식 방법을 뜻하지 않는다.
- **Analyst generalization / 분석자 일반화:** 아래의 열 블록 문법, 추상어 변환, 충돌 우선순위, 모호한 요청 분기 규칙은 위 관찰을 재사용 가능한 프롬프트 설계 절차로 바꾼 이 프로젝트의 권장안이다. 모든 게시물에 적용되는 사실이나 계정의 공식 알고리즘이 아니다.
- **Low-evidence extension / 근거가 약한 확장 적용안:** 계정별 근거가 충분하지 않은 피사체 유형에는 핵심 문법만 확장 적용할 수 있다. 그런 적용은 강한 계정별 표본을 벗어난 확장임을 명시하며, 확립된 계정 패턴으로 소개하지 않는다.

이 문서는 원문 프롬프트를 복제하는 자료가 아니라, 짧고 독창적인 설계 규칙이다.

## Input Schema

작성을 시작하기 전에 다음 입력을 수집한다. 사용자가 주지 않은 첨부 이미지의 내용은 추정하지 않는다.

- 목적/사용처: `[purpose/use]`
- 주제 또는 피사체: `[subject]`
- 반드시 유지할 정체성·형태·구조·문구: `[must-keep identity/shape/text]`
- 출력 수, 화면비, 각 결과의 독립 출력 여부, 콜라주 여부: `[output count and aspect ratio]`
- 분위기와 방향: `[mood/direction]`
- 사용할 색과 금지할 색: `[colors and forbidden colors]`
- 텍스트 사용 여부, 정확한 문구, 언어: `[text/no-text/exact text and language]`
- 첨부물 목록, 각 이미지의 역할(content source / style-layout target / generated result / region-mask), 이미지별 개별 처리 또는 콜라주 처리: `[attachments, roles, and handling]`
- 지정 이미지 모델: `[named image model]`

## Ten-Block Order

**Analyst generalization / 분석자 일반화:** 다음 기본 순서는 계정 관찰 패턴을 실제 작성 절차로 운용하기 위한 프로젝트 권장안이다. 각 블록은 하나의 구별되는 역할만 맡고, 같은 지시를 여러 블록에서 반복하지 않는다.

1. **output contract** — 개수, 화면비, 독립 출력, 콜라주 상태;
2. **first-glance visual thesis** — 장면과 대비가 첫눈에 읽히는 방식;
3. **subject preservation** — 바뀌면 안 되는 정체성, 형태, 구조, 텍스트;
4. **composition grammar** — 위치, 크기, 축, 겹침, 가림, 여백;
5. **medium and making actions**;
6. **color system** — 색 개수와 각 색의 역할 및 대략적 면적;
7. **typography when needed** — 제목/보조 문구, 언어, 역할, 배치;
8. **light, material, surface, print, or rendering traits**;
9. **concrete emotional finish**;
10. **only the restrictions for likely failures in that direction**.

## Type-Specific Order Changes

기본 논리는 유지하고 아래 변화만 통제해서 적용한다.

- 텍스트 없는 작업은 7번을 생략하고, 임의의 글자·숫자·로고·워터마크·서명·라벨을 만들지 말라고 명시한다.
- 제품 또는 참고 이미지 작업은 3번을 특히 구체화한다. 제공된 근거에 따라 실루엣, 비율, 확인된 재료 또는 보이는 재질 외관, 색 배치, 스티치, 밑창을 적고, 로고는 사용자가 제공한 경우에만 보존한다. 첨부 이미지의 픽셀에서 직접 보이는 외관과 사용자가 확인한 물리적 재료·사양을 구분한다. 픽셀만으로 재료가 확정되지 않으면 `어두운 투명 패널`, `브러시드 메탈처럼 보이는 표면`처럼 외관으로 표현한다. `강화유리`, 정확한 재료, 제조 방식, 브랜드·모델, 숨은 내부 구조는 사용자가 제공하거나 확인한 경우에만 단정한다.
- 참고 이미지 작업은 [reference-image-fidelity.md](reference-image-fidelity.md)에 따라 첨부물 역할을 먼저 정하고, 보존/변형/무시 목록을 분리한다. content source는 정체성을, style-layout target은 관찰 가능한 스타일과 배치만 통제한다.
- 참고사진에 우연히 보이는 QR 코드, 바코드, UI, 워터마크, 무관한 간판, 떠도는 작은 글자는 사용자가 요구하지 않는 한 하단 장식이나 타이포그래피로 재사용하지 않는다.
- 분할 비율, 피사체 수, 구조 단계 수, 제목 위치·줄 수, 보조 라벨 수와 여백은 하나의 geometry contract에 한 번만 적고 다른 블록에서 수치로 반복하지 않는다. 비율·여백·경계 같은 연속 수치는 사용자 값 또는 파일·픽셀 측정만 `정확히`로 쓴다. 피사체·단계·줄·라벨 같은 이산 개수는 사용자 값, 화면에서 직접 센 값, 또는 명시적인 디자인 선택으로 고정할 수 있으나 그 출처를 구분한다. 눈대중 연속 수치는 `약`으로 표시한다.
- 여러 사진은 사용자가 콜라주를 요청하지 않는 한 서로 분리된 독립 결과로 처리한다.
- 반복 시리즈는 변하지 않는 문법과 주제·날짜·도시·언어 같은 가변 항목을 나눈다.
- 명시적 보존 조건보다 스타일 선택을 앞세우지 않는다.
- 비사진 작업에는 카메라나 렌즈 세부사항을 추가하지 않는다.

## Abstract-to-Visual Conversion

“프리미엄”, “감각적”, “미니멀” 같은 모호한 말은 보이는 관계로 바꾼다. 위치, 크기, 가장자리, 겹침, 재료의 반응, 빛의 방향, 색의 역할, 정보 밀도를 구체적으로 적는다.

- 스타일 이름은 제작 동작으로 펼친다: 자르기, 접기, 층 쌓기, 어긋나게 인쇄하기, 선 끊기, 입자 흩뿌리기.
- 색은 형용사 목록이 아니라 **색 개수 + 기능적 역할 + 대략적 면적**으로 정의한다. 예: `[base color] 70% 배경`, `[accent color] 20% 초점`, `[signal color] 10% 작은 강조`.
- 품질을 높이는 수식어를 쌓기보다 요소가 서로 어떻게 보이고 반응하는지 적는다.

## Conflict Resolution

서로 충돌하는 지시를 숨기지 말고 먼저 드러낸 뒤, 사용자가 다른 우선순위를 명시하지 않았다면 다음 순서로 해결한다.

1. 명시적 must-keep 요구사항
2. 목적
3. 보조 스타일 선택

최종 출력에는 선택한 해결책을 짧게 밝힌다. 정확하고 읽을 수 있는 문구, 유사 문자, 바코드, 번호 생성은 실패 위험을 알리고 텍스트 없는 레이아웃 또는 후반 편집 대안을 제안한다. no-text 요청에는 임의의 텍스트, 숫자, 로고, 워터마크, 서명, 라벨을 금지한다.

참고 이미지 충돌에서는 content source의 명시적 보존 목록이 style-layout target보다 우선한다. 타깃의 피사체, 로고, 문구 또는 숨은 구조를 source에 덮어쓰지 않는다. 정확한 화면 분할과 자유로운 재구성이 충돌하면 사용자가 요구한 수치 계약을 유지하고, 자유도는 허용된 영역 내부로 제한한다.

## Comparison-to-Revision Mode

생성 결과와 참고 또는 타깃이 함께 주어지면 먼저 보이는 차이와 성공을 분리하고, [quality-check.md](quality-check.md)의 선택적 시각 루브릭을 적용한다. 실패를 해당 블록 하나에 매핑하여 그 블록만 수정하고, 정상인 보존 조건·색·재질·구성을 불필요하게 다시 쓰지 않는다. 비교표 다음에는 일반 출력 계약에 맞는 상세 수정 프롬프트, 짧은 수정 프롬프트, 정확히 세 개의 편집 변수와 적용 이유를 제공한다.

## Ambiguous Request Diversification

다섯 필드인 **purpose, subject, format, mood/style, preservation requirements**를 확인한다.

- 세 개 이상이 비어 있으면 모호한 요청이다. 질문 때문에 멈추지 말고 정확히 네 개의 완성된 방향을 반환한다.
- 비어 있는 필드가 두 개 이하이면 불필요하게 확장하지 않고 추천 방향 하나를 반환한다.
- 네 방향의 모든 쌍은 정확히 다음 일곱 축 중 최소 네 축에서 달라야 한다: **medium, layout, color, typography, texture, mood, rendering**.
- 배경색, 제목, 형용사만 바꾸는 것은 차이로 세지 않는다.

각 방향에는 **방향 이름, 시각 논지, 상세 프롬프트, 짧은 프롬프트, 선택적 네거티브 프롬프트, 정확히 세 개의 편집 변수, 적용 이유**를 모두 넣는다. 네 방향을 만든 뒤 6개 방향 쌍 각각의 차이를 일곱 축으로 대조하여 최소 네 축 차이를 확인한다.

## Model Syntax Boundary

파라미터, 스위치, 플래그, 스텝, CFG, 시드 값 등 모델 전용 문법은 사용자가 지정한 모델에서 직접 지원됨이 확인된 경우에만 추가한다. 확인되지 않으면 자연어 지시를 쓰고 해당 문법을 `확인 불가`로 표시한다. 설정을 추측하거나 만들어내지 않는다.
